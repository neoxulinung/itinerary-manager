# 旅行規劃管理助手 — User Story

## 專案背景

旅遊揪團（2人小團～10人左右）的行程討論全部發生在 LINE 群組裡，缺乏結構化整理。本專案做一個被動加入 LINE 群組的 Bot，自動把討論內容整理成「已決定／未定事項」的時間軸，並支援指令式的溯源問答，透過 LIFF 頁面隨時查看整理結果。

## 範圍與規模

- 個人／朋友團規模使用，非多租戶 SaaS。
- MVP 聚焦：自動整理已定/未定事項、指令式溯源問答。不含主動提醒、投票、網路搜尋協助（後續可擴充）。
- 主機：雲端代管（serverless/小主機 + 物件儲存），具體服務於 Plan 階段決定。

## 核心設計決策

### 旅程生命週期
- Bot 加入群組後預設「潛水」，不記錄任何訊息。
- `/旅程 開始 <名稱>` → 開始記錄整理；下指令者自動成為該趟旅程的主揪。
- `/旅程 結束` → 只有主揪能下，停止記錄，回到潛水狀態。
- 忘記結束不做自動偵測，純手動指令控制（MVP 先這樣，之後可加）。
- 同一群組可重複開新旅程，各趟資料彼此獨立不混雜。

### 互動方式：全部指令化，不做自由文字觸發
Bot 絕不主動或憑自由文字語意插話，所有「Bot 開口說話」都必須是明確指令觸發：
- `/旅程 開始 <名稱>`
- `/旅程 結束`
- `/問 <問題>` — 針對特定問題查詢，回答附原始訊息出處
- `/未定事項` — 列出目前尚未決定的事項清單
- 背景的訊息分類（已定/未定判斷、照片與連結擷取）仍是被動全自動處理，這是唯一不需指令的部分；差別在於「整理」是自動的，「Bot 回話」永遠需要指令觸發。

### LIFF 懶人包：即時可看，不綁旅程結束
- LIFF 頁面反映「目前進行中旅程」的即時整理狀態，旅程進行中隨時打開都看得到最新內容，不需等 `/旅程 結束`。
- 建議透過 LINE Rich Menu 固定一個「查看行程」按鈕開啟 LIFF，隨時可用；沒有進行中旅程時顯示上一趟的最終結果或空狀態。
- `/旅程 結束` 的作用是停止繼續記錄新內容，LIFF 上的資料會定格在結束當下的整理結果。

### 照片備份
- Bot 收到圖片訊息當下立即下載原始檔案（LINE 對訊息內容的下載時效有限），存入雲端物件儲存，與該筆整理事項綁定。
- 不設保留期限，長期保留。

### 權限
- `/旅程 開始/結束` 僅該趟旅程的主揪（即下 `/旅程 開始` 的人）可操作。
- `/問`、`/未定事項` 全員皆可使用。

## Epic A｜旅程與訊息整理

- **US-A0** 作為團員，我可以用 `/旅程 開始 <名稱>` 開始一趟旅程，我自動成為這趟旅程的主揪。
- **US-A0b** 作為主揪，我可以用 `/旅程 結束` 結束目前旅程，停止繼續記錄新內容。
- **US-A1** 作為團員，旅程進行中 Bot 會持續被動記錄群組訊息，我不用額外操作。
- **US-A2** 作為團員，系統能自動判斷一則訊息是否為旅遊相關事項（行程/住宿/交通/餐廳等），並分類成「已決定」或「討論中/未定」。
- **US-A3** 作為團員，整理出的事項會保留原始訊息附的照片（已備份於雲端）與連結。
- **US-A5** 作為主揪，已決定事項會自動整理成按日期排列的時間軸（Day1, Day2...）。

## Epic B｜指令式溯源問答

- **US-B1** 作為團員，我可以用 `/問 <問題>`（例如「我們訂哪天的機票？」）向 Bot 查詢，Bot 依整理好的資料回答。
- **US-B2** 作為團員，Bot 回答時附上原始訊息出處（誰、何時說的、連結回原文），方便我回去確認。
- **US-B3** 作為團員，若查無資料或事項尚未定案，Bot 明確回覆「還沒決定/不確定」，不能瞎猜。
- **US-B4** 作為團員，我可以用 `/未定事項` 指令查詢目前所有尚未決定的事項清單。

## Epic C｜LIFF 懶人包

- **US-C1** 作為團員，透過 Rich Menu 開啟 LIFF，能看到目前進行中旅程依日期排列的時間軸（景點/交通/住宿），即時更新。
- **US-C2** 作為團員，同一頁面能看到「未定事項」清單。
- **US-C3** 作為團員，點進某個行程項目能看到相關的原始討論、照片、連結。

## 新增功能（MVP完成後）：記帳分攤與投票

這兩個功能跟 Epic A-C 不同：使用頻率高、需要重複挑選/操作特定項目（哪一筆帳目、哪個選項），純聊天指令會洗版、也難表達「編輯第幾筆」。改採**混合式**：

- **開始/結束這種一次性宣告動作**、以及**新增**（打字當下最快，不太會洗版）→ 聊天指令與LIFF**並存**，兩邊都能做，方便使用者當下用哪個順手就用哪個。
- **編輯、刪除、投票/取消投票**這種需要重複操作或挑選特定項目的 → **只在LIFF**，避免洗版。
- **查詢類**（結算、投票結果）→ 聊天指令與LIFF並存。

| 動作 | 聊天指令 | LIFF |
|---|---|---|
| 記帳：新增帳目 | ✅ | ✅ |
| 記帳：編輯/刪除 | ❌ | ✅ |
| 記帳：結算 | ✅ | ✅ |
| 投票：開始 | ✅ | ❌ |
| 投票：新增選項 | ✅ | ✅ |
| 投票：投票/取消 | ❌ | ✅ |
| 投票：查結果 | ✅ | ✅ |
| 投票：結束 | ✅ | ❌ |

因為要支援LIFF上的編輯/投票等寫入動作，LIFF頁面需要從目前的「唯讀顯示」升級成「知道是誰在操作」——用`liff.getProfile()`（已申請`profile` scope）取得操作者身分，這是原本MVP刻意跳過、現在因為這兩個功能需要而要補上的部分。

### Epic D｜記帳分攤

- **US-D1** 作為團員，我可以用 `/記帳 <金額> <說明> [@人1 @人2...]` 或在LIFF頁面上用表單，記一筆代墊款項——我自己是付款人；有 @人（或勾選）就只有那些人分攤，沒指定就由「這趟旅程期間有在群組裡發言過的所有人」一起分攤。
- **US-D2** 作為團員，我可以在LIFF頁面上看到所有帳目列表，並編輯或刪除記錯的項目。
- **US-D3** 作為團員，我可以用 `/結算` 或在LIFF頁面上，隨時查詢目前每個人的淨收支狀況，以及系統算好的最少轉帳建議（例如「小華付給小明 500元」）。
- **US-D4** 作為團員，`/旅程 結束` 時 Bot 會自動附上最終結算結果。

**技術限制/MVP先不做**：單一貨幣、不處理匯率；金額換算除不盡時可能有一兩分錢的極小誤差（業界常見做法，不追求分毫不差）；「全部參與者」用發言記錄推算，不是LINE群組正式成員名單（因為列出完整成員名單的API限「已驗證/付費帳號」才能用，我們的一般帳號用不了）。

### Epic E｜投票

- **US-E1** 作為團員，我可以用 `/投票 開始 <題目>` 開一個新投票，同時間一個群組只能有一個進行中的投票，且投票綁定在進行中的旅程底下。
- **US-E2** 作為團員，我可以用 `/投票 新增 <選項>` 或在LIFF頁面上，隨時加入候選選項，即使已經有人開始投了也能加。
- **US-E3** 作為團員，我可以在LIFF頁面上投給想選的選項，可複選；對同一個選項再點一次會取消那一票（可以改變心意）。
- **US-E4** 作為團員，我可以用 `/投票 結果` 或在LIFF頁面上，隨時查看目前每個選項的得票狀況、以及是誰投的（不匿名，這樣才知道誰要跟誰一起行動）。
- **US-E5** 作為團員，我可以用 `/投票 結束` 鎖定結果，之後不能再投票或加選項——任何人都能結束，不限發起人。

## 待 Plan 階段釐清的技術問題

1. LINE Messaging API 在群組中被動讀取全員訊息的可行性與方案費用（需查證，而非假設）。
2. 訊息分類（已定/未定）與問答的 LLM 處理方式與成本。
3. 資料模型：旅程(Trip) / 事項(Item) / 原始訊息(Message) / 附件(Attachment) 的關聯設計。
4. 雲端服務選型：webhook 主機、資料庫、物件儲存。
5. LIFF 頁面即時性怎麼實現（輪詢 vs 推播更新）。
